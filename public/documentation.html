Authentication

API key setup, encrypted identifiers, rate limits, and idempotency

API Key Authentication

All API requests require an API key passed via the X-API-KEY header.

X-API-KEY: your-api-key-here

Requests without a valid API key return 401 Unauthorized.

Encrypted Identifiers

All entity IDs in URL paths ({encryptedIdentifier}) are OpenSSL AES-256-CBC encrypted strings. The server decrypts them transparently. Use POST /api/v1/encrypt to generate encrypted IDs.

Idempotency

Write operations support idempotency via the Idempotency-Key header (max 64 chars). Replays within 24h return cached response. Different body with same key returns 409 Conflict.

Idempotency-Key: unique-request-id-123

Returns up to 10 of the customer's most recent entries of each type, newest first. There is no date window and no pagination. Each row is one game or competition wallet, not one transaction.

To file a complaint with POST /complaints:

POST/api/v1/withdraw/{encryptedIdentifier}Withdraw from customer wallet to M-Pesa (B2C payout)▶
API KeyEncrypted IDIdempotent5/min

Description

Performs the actual M-Pesa B2C payout from the customer's wallet to their registered phone number. The wallet is debited and a withdrawal ledger entry is recorded up front, then the B2C request is sent. If M-Pesa rejects the request or errors, the debit is reversed against that ledger entry and the withdrawal is marked as failed (disburse 3) with the error message stored.

Request Body

FieldTypeRequiredDescription
amountnumericRequiredAmount to withdraw (min: 1). Must not exceed the wallet balance

Response (201)

{"status": "success", "ledger_entry_id": "LE-000123"}

Errors

StatusDescription
400Insufficient wallet balance for withdrawal or Customer phone number not found
404Customer not found or Wallet not found
422Validation failed. status holds the field errors
500M-Pesa B2C failed. The debit is reversed and status holds the error message

What the finance endpoints are

Everything under /api/v1/finance/ reports on money: income, cash flow, what is owed to customers, and where the numbers come from. All endpoints are read-only GET requests except recording and voiding expenses and excise duty remittances. They all need the X-API-KEY header.

Successful responses use the same envelope as the statistics endpoints. Reports over a range include a meta block; every report includes generated_at.

"pagination": {"page": 1, "per_page": 50, "total": 132, "last_page": 3}

Money is a number in KES rounded to 2 decimals. Validation errors return 422; see Error Responses.

Dates and time zone

Days are Nairobi days (Africa/Nairobi). A range covers whole days from 00:00 on from to 23:59:59 on to. "Today" ends at Nairobi midnight, not UTC midnight.

Ledger start date and warnings

Revenue, stakes, payouts and balances come from the ledger, which began recording on 2026-09-01. Cash in and cash out come from payment records and cover earlier dates. When a range starts before the ledger began, meta.warnings says which figures are zero before that date.

Escrow releases (game and competition payouts leaving their wallets) were only ledgered from a later date, so the trial balance and escrow checks may not balance before it. The warning appears in meta.warnings too.

Test customers

Reports can leave out test customers listed on the server in FINANCE_TEST_CUSTOMER_IDS. There are none by default, so in production every customer is included. When some are listed, reports leave them out unless you send exclude_test=0. The house wallet is always kept apart from customer wallets, whatever this list says. House cuts cannot always be tied to a player, so the income statement only removes cuts it can link to a test customer or a game a test customer played.

Caching and rate limits

Reports whose range includes today are cached for about 2 minutes, so a figure can lag by that long. Closed ranges and past balance sheets are cached for an hour. The drill-down lists are not cached. Finance GET endpoints share the stats limit of 20 requests per minute; recording or voiding an expense or an excise duty remittance uses the write limit of 30 per minute.

Privacy

Phone numbers are masked in JSON and CSV output, for example 254712345678 becomes 2547****5678. This includes phone-like values inside account references. Customer names are shown; use customer_id to look a customer up elsewhere.

Excise duty of 5% is taken from every plain M-Pesa deposit into a customer wallet (C2B confirmation, STK deposits and POST /deposits). A KES 100 deposit is credited in full, then KES 5.00 is debited as excise_duty, leaving KES 95.00. The duty is rounded half up to the cent and there is no minimum deposit. Coin loads, gifts, emoji and deposits from unknown customers are not charged. The duty is not revenue: it is held as excise_duty_payable on the balance sheet until you pay KRA and record a remittance. Returns and payment are due by the 20th of the following month. Excise duty is switched on and dated on the server (FINANCE_EXCISE_DUTY_ENABLED, FINANCE_EXCISE_DUTY_EFFECTIVE_FROM); deposits before the start date are never charged. The rate is saved on each charge.
The summary and charges list follow exclude_test like other reports. The payable amount, monthly returns and remittances always cover every customer, because that is what is owed to KRA. When a deposit is refunded, its excise duty is given back unless it has already been remitted. All GET endpoints are rate-limited to 20 requests/minute and can be downloaded as CSV from /finance/export/{report}.
